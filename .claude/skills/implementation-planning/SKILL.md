# Implementation Planning

## 目的

受入条件を満たすための実装と検証を、実行可能な計画にする。

## 入力

対象Issueと分析結果:

$ARGUMENTS

## 参照

- docs/architecture.md
- docs/domain.md
- docs/standards/architecture-guidelines.md
- docs/standards/testing-strategy.md
- 関連コードとテスト

## 手順

1. IssueのReady条件と分析結果を確認する。
2. 受入条件ごとに必要な変更を整理する。
3. 既存の責務と依存を確認する。
4. 実装方式を選び、重要な選択には代替案と理由を付ける。
5. 変更ファイルと新規作成予定を分けて示す。
6. API、DB、依存追加、環境変数への影響を整理する。
7. テスト層、ケース、実行コマンドを決める。
8. 移行が必要なら順序、バックアップ、復旧方法を記載する。
9. 作業順序と完了判定を示す。

## 出力

### 目的と範囲

対象内、対象外、前提。

### 実装方針

採用する方式と理由。
重要な代替案とトレードオフ。

### 変更対象

ファイルまたは責務ごとの変更内容。
存在しないファイルは新規予定と明記する。

### 受入条件と検証

各受入条件に対応するテストと期待結果。

### 作業順序

依存関係を考慮した実装順。

### 移行・運用

データ、環境変数、互換性、復旧への影響。

### 判断待ち

未解決の判断と、それに依存する作業。

## 完了条件

- 全受入条件に実装・検証の方針がある
- 変更範囲が明確である
- 重要な影響と未決事項が明示されている

## 作業範囲

計画だけの依頼ではコードを変更しない。
合意済みの方針を再び承認待ちにしない。
