# Implementation

## 目的

Issueの受入条件を満たす変更を実装する。

## 入力

対象Issueと実装計画:

$ARGUMENTS

## 参照

- docs/product.md
- docs/domain.md
- docs/architecture.md
- docs/standards/definition-of-done.md
- 関連コードとテスト
- 適用されるRules

パスはプロジェクトルートを基準とする。

## 手順

1. 作業ツリーと既存変更を確認する。
2. Issue、受入条件、計画を照合する。
3. 実行環境と既存の実装方法を確認する。
4. 重要な仕様不足があれば、依存する作業を止めて判断材料を示す。
5. 既存設計に沿って必要最小限の変更を実装する。
6. 関連する回帰・境界・異常系テストを追加する。
7. 対象に近いテストを実行する。
8. 変更が安定したら必須チェックを行う。
9. 仕様、設定、実行方法の変更を文書へ反映する。
10. 差分を確認し、不要な変更や秘密の混入を除く。
11. 受入条件への対応と残課題を報告する。

## 計画変更

変更が必要なら理由と影響を説明する。
受入条件や公開契約が変わる場合は、Issueと計画を更新する。

通常の内部実装は、既存方針に沿って判断する。

## 出力

- 変更概要
- 受入条件への対応
- 主要な変更箇所
- 実行した検証と結果
- 未検証範囲
- 残課題
- 現在の完了状態

## 完了条件

- 対象範囲の変更が揃っている
- 必要な検証を行っている
- 未達事項が明示されている
- レビュー可能な差分になっている

## 操作範囲

Skillの呼び出しだけを、push、外部投稿、
マージ、デプロイの許可と解釈しない。

依頼された外部操作は、その範囲で実行する。
