# Implementation

## 目的

Issueの受入条件を満たす変更を実装する。

## 入力

対象Issueと実装計画:

$ARGUMENTS

## 参照

- docs/product.md
- docs/domain.md
- docs/architecture.md
- docs/stack.md
- docs/standards/definition-of-done.md
- 関連コードとテスト
- 適用されるRules

## 手順

1. 作業ツリーと既存変更を確認する。
2. Issue、受入条件、計画を照合する。
3. 重要な仕様不足があれば依存する作業を止め、判断材料を提示する。
4. 既存設計に沿って必要最小限の変更を実装する。
5. 関連する回帰・境界・異常系テストを追加する。
6. 対象に近いテストを実行する。
7. 変更が安定したら必須チェックを実行する。
8. 仕様、API、環境設定、実行方法の変更を文書へ反映する。
9. 差分を確認し、秘密・不要生成物・無関係な変更を除く。
10. 受入条件ごとの対応と残課題を報告する。

## 計画変更

変更が必要になった場合は、理由と影響を説明する。
受入条件や公開契約が変わる場合は、Issue・計画を更新する。
内部実装の通常の判断は、既存設計に合わせて進める。

## 出力

- 変更概要
- 受入条件への対応
- 変更した主要ファイル
- 実行コマンドと結果
- 未検証範囲
- 残課題
- 現在の完了状態

## 完了条件

- 対象範囲の変更が揃っている
- 必要な検証が実行されている
- 未達事項が明示されている
- レビュー可能な差分になっている

## 操作範囲

Skillの呼び出しだけを、push、外部投稿、マージ、
デプロイの許可と解釈しない。
依頼された外部操作は、その範囲で実行する。
