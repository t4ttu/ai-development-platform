# コードレビュー標準

## 1. 目的

仕様との不一致、不具合、データ破壊、認可漏れ、
互換性問題、検証不足を変更の確定前に検出する。

コードの好みだけを押し付ける場にしない。

## 2. 入力

- 対象Issue
- PRまたは比較範囲
- 変更差分
- 関連コード
- 関連仕様
- テスト結果
- 移行・運用手順

未コミット差分、ブランチ差分、PR差分のどれを確認したか明示する。

## 3. 確認順序

1. 目的と受入条件
2. 動作と境界条件
3. 認証・認可・データ保護
4. データ整合性
5. 互換性と移行
6. テスト
7. 保守性と変更範囲
8. ドキュメント

## 4. 主な観点

### 要求

- 受入条件を満たしているか
- 対象外の変更が混ざっていないか
- 未決仕様を勝手に確定していないか

### 正しさ

- 問題になる入力や状態を扱えているか
- 失敗時に不整合が残らないか
- 再実行や同時更新で問題が起きないか

### セキュリティ

- 外部入力を検証しているか
- リソース単位の認可があるか
- 秘密や個人情報が露出しないか
- 外部通信やファイル操作の範囲が適切か

### テスト

- 変更した振る舞いを確認しているか
- 不具合を検出できる期待値か
- 重要な境界と異常系が不足していないか
- テストを弱めて成功させていないか

### 保守性

- 責務が明確か
- 無関係な変更が混ざっていないか
- 過剰な抽象化や依存追加がないか
- 既存規約と整合しているか

## 5. 指摘の形式

- 重大度
- ファイルと位置
- 発生条件
- 問題となる動作
- 影響
- 根拠
- 修正方向

事実と仮説を分ける。
同じ原因の指摘を重複させない。

## 6. 重大度

### P0

即時対応が必要な重大障害、漏えい、広範囲のデータ破壊。
通常のレビュー待ちにせず責任者へ伝える。

### P1

マージ前に修正すべき重大な機能不全、認可漏れ、
データ破壊、主要フローの失敗。

### P2

通常の修正対象となる不具合や重要な検証不足。

### P3

任意の改善。
規約違反と個人の好みを区別する。

## 7. 修正後の確認

- 原因が解消しているか確認する
- 必要な回帰テストを追加する
- 新しい影響を確認する
- 必要なチェックを再実行する

見送る指摘には理由、担当者、追跡先を記録する。

## 8. 結果

指摘がない場合も次を記載する。

- 確認した範囲
- 実行した検証
- 未検証範囲
- 残るリスク

「指摘なし」は無欠陥の保証ではない。

## 9. 責任分担

- AI：差分調査、問題検出、根拠の提示
- 人間：最終承認、受入判断、見送るリスクの判断

AIレビューだけを人間の受入完了とみなさない。

## 10. 操作範囲

レビュー依頼だけで、コード変更、外部投稿、マージを行わない。
依頼されている場合は、その範囲で行う。
