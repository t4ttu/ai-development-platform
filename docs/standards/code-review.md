# コードレビュー標準

## 1. 目的

受入条件との不一致、不具合、データ破壊、認可漏れ、
互換性問題、検証不足を変更の確定前に検出する。

コードの好みだけを押し付ける場にしない。

## 2. 入力

- 対象Issue
- Pull Requestまたは比較範囲
- 変更差分
- 関連コード
- 関連仕様
- テスト結果
- 移行・運用手順

未コミット差分、ブランチ差分、PR差分のどれを確認したか明記する。

## 3. 確認順序

1. 目的と受入条件
2. 実際の動作
3. 異常系・境界条件
4. 認証・認可・データ保護
5. データ整合性
6. API・DBの互換性と移行
7. テストの妥当性
8. 保守性と変更範囲
9. ドキュメント

## 4. 主な観点

### 要求との整合性

- すべての受入条件を満たしているか
- 対象外の変更が混ざっていないか
- 未決仕様を勝手に確定していないか

### 正しさ

- 実際に問題になる入力や状態を扱えているか
- 例外時に不整合が残らないか
- 同時実行や再実行で問題が起きないか

### セキュリティ

- 入力境界が検証されているか
- リソース単位の認可があるか
- 秘密や個人情報が露出しないか
- 外部通信やファイル操作の範囲が適切か

### テスト

- 変更した振る舞いを検証しているか
- 不具合を実際に検出できる期待値か
- 重要な境界や異常系が不足していないか
- テストを弱めて成功させていないか

### 保守性

- 責務が分かれているか
- 無関係な変更が混ざっていないか
- 過剰な抽象化や依存追加がないか
- 既存規約と整合しているか

## 5. 指摘の書き方

各指摘に次を含める。

- 重大度
- ファイルと行
- 発生条件
- 問題となる動作
- 利用者やデータへの影響
- 根拠
- 修正方向

根拠が不足する場合は、事実と仮説を分ける。
同じ原因の指摘を重複させない。

## 6. 重大度

### P0

即時対応が必要な重大な障害、漏えい、広範囲のデータ破壊。
通常のレビュー待ちにせず責任者へ伝える。

### P1

マージ前に修正すべき重大な機能不全、
認可漏れ、データ破壊、主要フローの失敗。

### P2

通常の修正対象となる不具合や重要な検証不足。

### P3

任意の改善。
既存規約への違反と、レビュアー個人の好みを区別する。

## 7. 修正後の確認

- 指摘の原因が解消されたか確認する
- 必要な回帰テストを追加する
- 修正による新たな影響を確認する
- 必要なチェックを再実行する

指摘を見送る場合は、理由、担当者、追跡Issueを記録する。

## 8. レビュー結果

問題が見つからなかった場合も、次を記載する。

- 確認した範囲
- 実行した検証
- 未検証の範囲
- 残るリスク

「指摘なし」は、無欠陥の保証ではない。

## 9. 責任分担

- AI: 差分調査、問題の検出、根拠の提示
- 人間: 最終承認、受入判断、見送るリスクの判断

AIレビューのみを、人間の受入完了とみなさない。

## 10. 操作範囲

レビュー依頼だけで、コード変更、コメント投稿、マージを実行しない。
それらが依頼されている場合は、許可された範囲で行う。
