# Definition of Done

## 1. 目的

Issueを完了したと判断するための共通基準を定義する。

「コードを書いた」「テストが一つ通った」「PRを作った」だけでは、
Issue完了とはしない。

## 2. 適用

機能追加、バグ修正、技術タスクに適用する。

文書のみ、調査のみなど、適用しない項目がある場合は、
対象外の理由と代わりの確認方法を記録する。

プロジェクトは追加条件を定義できる。
共通の必須条件を黙って削除しない。

## 3. 要求と実装

- [ ] Issueの目的を達成している
- [ ] すべての受入条件を満たしている
- [ ] 対象外の変更が混ざっていない
- [ ] 重要な未決仕様が残っていない
- [ ] 必要なエラー・境界条件を扱っている

## 4. テストと検証

- [ ] 必要なテストを追加・更新した
- [ ] 必須チェックが成功している
- [ ] 既存機能への影響を確認した
- [ ] 必要なビルド・型検査・静的解析を確認した
- [ ] 実行コマンドと結果を記録した
- [ ] 未実施項目と理由を明記した
- [ ] 未検証事項を成功扱いしていない

## 5. セキュリティとデータ

- [ ] 必要な入力検証と認可を確認した
- [ ] 秘密や個人情報を差分・ログ・証跡へ含めていない
- [ ] データ整合性への影響を確認した
- [ ] 必要な移行・バックアップ・復旧方法を用意した

## 6. レビュー

- [ ] 対象差分のレビューが完了した
- [ ] 重大な指摘が解消している
- [ ] 修正後の必要な再検証が完了した
- [ ] 見送った指摘に理由と追跡先がある

## 7. ドキュメント

- [ ] 変更した仕様を更新した
- [ ] API・DB・環境変数の変更を記録した
- [ ] 起動・検証・運用方法の変更を反映した
- [ ] 関連Issue・PR・設計判断を辿れる

## 8. 受入と完了操作

- [ ] 人間による受入が完了した
- [ ] Pull Requestが承認された
- [ ] Pull Requestがマージされた
- [ ] Issueの状態と実際の結果が一致している
- [ ] 残作業は後続Issueで追跡できる

## 9. 状態の区別

次の状態を区別して報告する。

- 実装完了
- 検証完了
- レビュー待ち
- 受入済み
- マージ済み
- リリース済み

本番反映をしていない場合は、リリース済みと報告しない。

## 10. 例外

必須条件を満たせない場合は、次を記録する。

- 未達項目
- 理由
- 影響とリスク
- 代替措置
- 判断した責任者
- 解消期限
- 追跡Issue

未達項目がある状態を、通常のDoD達成と同じ表現で報告しない。
例外として受け入れたことを明示する。
