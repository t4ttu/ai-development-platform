# AI駆動開発 標準ワークフロー

## 1. 目的

本ドキュメントは、AI Coding Agentを活用した
ソフトウェア開発の標準プロセスを定義する。

以下を実現することを目的とする。

- 開発工程の標準化
- AIと人間の責任分担の明確化
- 開発品質の維持
- 手戻りの削減
- 複数プロジェクトでの再利用

## 2. 基本方針

- アジャイル開発を基本とする
- ユースケース駆動開発を採用する
- GitHub Issuesを開発管理の中心とする
- Issue単位で設計・実装・テストを行う
- AIは開発作業を支援し、重要な意思決定は人間が行う
- 必要最小限のドキュメントを維持する
- すべての変更は受入条件に基づいて検証する

工程は責務と判断を明確にするための区分である。
小さな変更では分析・計画・検証結果を同じIssueやPRにまとめてよい。

記録をまとめることと、
必要な判断や検証を省略することは区別する。

## 3. 開発工程

開発は以下の工程で実施する。

1. 要求整理
2. Issue作成
3. Issue分析
4. 実装計画
5. 実装
6. テスト
7. コードレビュー
8. 受入確認
9. 完了・振り返り

不具合や仕様不足が見つかった場合は、必要な工程へ戻る。

## 4. 工程定義

### 4.1 要求整理

#### 目的

ユーザーの課題と実現したい価値を明確にする。

#### インプット

- ユーザーの要望
- プロダクト方針
- 既存機能
- 既知の課題と制約

#### 実施内容

- 対象ユーザーと利用場面の整理
- ユーザーストーリーの整理
- ユースケースの洗い出し
- 提供価値の確認
- 対象範囲と対象外の整理
- 優先順位の検討

#### アウトプット

- ユーザーストーリー
- ユースケース一覧
- 優先順位
- product.mdの更新

#### 責任分担

- 人間：要求・提供価値・優先順位の決定
- AI：要求整理・ユースケース・不足情報の提案

#### 次工程へ進む条件

- 誰のどの課題を解決するか説明できる
- 実現したい結果が明確である
- 対象外が区別できる

### 4.2 Issue作成

#### 目的

開発対象を実装・検証可能な単位にする。

#### インプット

- ユースケース
- プロダクト方針
- 関連Issue
- 既知の制約

#### 実施内容

- Issueの作成
- 受入条件の定義
- 対象範囲・対象外の明確化
- 依存関係の整理
- 必要に応じたIssueの分割

#### アウトプット

- GitHub Issue
- 関連するユースケース・文書へのリンク

#### 責任分担

- 人間：Issueの目的・優先順位・受入条件の承認
- AI：Issue内容の具体化・分割案の提案

#### 次工程へ進む条件

- 目的、範囲、受入条件が記載されている
- 分析に必要な情報が揃っている
- 未決事項が明示されている

### 4.3 Issue分析

#### 目的

実装前に要求と既存システムへの影響を把握する。

#### インプット

- GitHub Issue
- 関連ドキュメント
- 既存ソースコード
- 既存テスト

#### 実施内容

- 受入条件の確認
- 関連機能と既存挙動の調査
- 不明点・矛盾の抽出
- 影響範囲の特定
- データ、権限、運用への影響確認
- 検証方法の見通しの整理

#### アウトプット

- Issue分析結果
- 不明点一覧
- 根拠付きの影響範囲
- リスク
- 実装着手可否

#### 責任分担

- 人間：重要な不明点と仕様上の選択の判断
- AI：調査・分析・判断材料の提示

#### 次工程へ進む条件

- 受入条件を検証可能な形で理解できる
- 実装結果を左右する不明点が解消している
- 主要な影響範囲が分かっている
- IssueがReady条件を満たしている

### 4.4 実装計画

#### 目的

実装方針と変更範囲を明確にする。

#### インプット

- 分析済みIssue
- アーキテクチャ
- 業務仕様
- 既存コード
- 開発ルール

#### 実施内容

- 実装方式の検討
- 変更する責務とファイルの特定
- データやインターフェース変更の検討
- 必要な依存追加の検討
- テスト方針の作成
- 作業順序の整理
- 必要に応じた移行・復旧方法の検討

#### アウトプット

- 実装計画
- テスト計画
- 受入条件と検証方法の対応
- 判断が必要な事項

#### 責任分担

- 人間：重要な設計変更・互換性変更・費用への影響の承認
- AI：実装計画・代替案・検証方針の作成

#### 次工程へ進む条件

- 何を変更するか説明できる
- 受入条件の検証方法が決まっている
- 必要な重要判断が完了している
- 移行が必要な場合、その順序と復旧方法が明確である

合意済みの方針について、同じ承認を繰り返し要求しない。

### 4.5 実装

#### 目的

受入条件に基づいて機能を実装する。

#### インプット

- GitHub Issue
- 実装計画
- 開発ルール
- 業務仕様
- 既存コードとテスト

#### 実施内容

- ソースコードの実装
- 必要なデータ構造の変更
- テストコードの追加・修正
- エラー処理と境界条件への対応
- 必要なドキュメント更新
- 差分の自己確認

#### アウトプット

- ソースコード
- テストコード
- 必要な移行ファイル
- 更新したドキュメント
- 変更概要

#### 責任分担

- 人間：実装中に生じた重要な判断
- AI：実装・関連テスト・文書更新

#### 次工程へ進む条件

- 計画した変更が揃っている
- 検証可能な状態になっている
- 明らかな未実装箇所が残っていない

計画と異なる変更が必要になった場合は、理由と影響を確認する。
仕様変更が必要なら、Issueと計画を更新する。

### 4.6 テスト

#### 目的

実装が受入条件を満たしていることを確認する。

#### インプット

- 受入条件
- テスト計画
- 実装コード
- テストコード
- 実行環境

#### 実施内容

変更に応じて、次から必要な検証を行う。

- 静的解析
- 型検査
- 単体テスト
- 結合テスト
- E2Eテスト
- ビルド確認
- 手動確認
- 不具合修正後の再検証

すべての変更に全種類を機械的に要求しない。
変更内容と失敗時の影響から必要な検証を選ぶ。

#### アウトプット

- 実行手順・コマンドと結果
- 受入条件ごとの検証結果
- 不具合一覧
- 未実施項目と理由

#### 責任分担

- 人間：重要な検証結果と例外の確認
- AI：テスト作成・実行・原因調査・修正

#### 次工程へ進む条件

- 必須チェックが成功している
- 受入条件に対応する証跡がある
- 未検証範囲が明示されている

不具合は実装へ戻して修正する。
要求の誤りが原因なら、要求・Issue・計画を見直す。

### 4.7 コードレビュー

#### 目的

実装の品質と設計上の妥当性を確認する。

#### インプット

- Pull Request
- GitHub Issue
- 変更差分
- テスト結果
- 関連仕様

#### 実施内容

- 仕様との整合性確認
- 動作と境界条件の確認
- コード品質の確認
- セキュリティ確認
- 変更範囲の確認
- 互換性と移行の確認
- テストの妥当性確認

#### アウトプット

- レビュー結果
- 修正指摘
- 残るリスクと未検証範囲

#### 責任分担

- 人間：最終承認
- AI：差分調査・問題の指摘・確認支援

#### 次工程へ進む条件

- 重大な指摘が解消している
- 修正後に必要な検証が行われている
- 見送った指摘には理由と追跡先がある

### 4.8 受入確認

#### 目的

ユーザー視点で要求が実現されていることを確認する。

#### インプット

- GitHub Issue
- 受入条件
- 動作するアプリケーション
- テスト結果
- レビュー結果

#### 実施内容

- ユースケースに沿った動作確認
- 受入条件の確認
- エラーや代替フローの確認
- 要求との差分の確認

#### アウトプット

- 受入結果
- 修正事項
- 後続Issueとして扱う改善事項

#### 責任分担

- 人間：受入判断
- AI：確認手順・証跡整理・問題調査の支援

#### 次工程へ進む条件

- すべての受入条件を満たしている
- 人間による受入が完了している

新たな要望は、現在の受入条件に含まれるかを確認する。
対象外の要望は後続Issueとして扱う。

### 4.9 完了・振り返り

#### 目的

開発結果を確定し、次の開発へ改善を反映する。

#### インプット

- 承認済みPull Request
- テスト結果
- 受入結果
- Definition of Done

#### 実施内容

- DoDの確認
- Pull Requestのマージ
- Issueの完了
- 課題・改善点の整理
- 必要な後続Issueの作成

#### アウトプット

- 完了Issue
- マージ済みコード
- 改善事項
- 後続Issue

#### 責任分担

- 人間：マージ・完了判断
- AI：結果整理・改善提案・許可された操作の実行支援

#### 完了条件

- DoDを満たしている
- マージとIssueの状態が一致している
- 必要な後続作業を追跡できる

マージ済みとリリース済みは区別する。

## 5. 工程の基本ルール

- IssueがReadyになる前に実装を開始しない
- 重要な仕様の不明点がある場合、その判断に依存する実装を止める
- 不明点に依存しない調査や検証準備は進めてよい
- 原則として1つのIssueに対して1つのPull Requestを作成する
- Issueの対象外となる変更は原則行わない
- テスト未実行の状態を成功として報告しない
- 受入条件を満たさないIssueは完了としない
- 不具合修正や仕様変更もIssueで管理する
- 他者の作業や既存変更を無断で消さない

Readyの詳細はissue-management.mdを参照する。

## 6. Definition of Done

Issueを完了するには、少なくとも以下を満たす。

- [ ] 受入条件を満たしている
- [ ] 必要なテストが成功している
- [ ] 既存機能への影響を確認している
- [ ] コードレビューが完了している
- [ ] 必要なドキュメントが更新されている
- [ ] 人間による受入が完了している
- [ ] Pull Requestがマージされている

詳細はdefinition-of-done.mdを参照する。
完了条件の正本はdefinition-of-done.mdとする。

## 7. 継続的改善

開発中に確認された問題は、次の観点で分類する。

- 要求・Issueの情報不足
- AIによる仕様の誤解
- アーキテクチャ・設計の問題
- Rulesの不足
- Skillsの不足
- テストの不足

複数プロジェクトで共通する問題は、
AI駆動開発基盤側の改善対象とする。

プロジェクト固有の問題は、
各プロジェクト内で解決する。

改善には、発生条件、原因、変更内容、確認方法を記録する。
一度の例外だけを理由に、すべてのプロジェクトを制約するルールを増やさない。

## 8. 記録の置き場所

- 要求と受入条件: Issue
- プロダクトの目的: docs/product.md
- 業務仕様: docs/domain.md
- 構成と実行方法: docs/architecture.md
- 重要な設計判断: 必要に応じてdocs/adr/
- 分析と計画: Issueコメントまたはdocs/work/
- 変更と検証結果: PR

同じ情報を複数箇所で正本として管理しない。
Issueから関連する記録へ辿れるようにする。
