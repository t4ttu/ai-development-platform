# Issue管理標準

## 1. 目的

要求、実装範囲、受入条件、進捗、完了状態をIssueで管理する。
人間とAIが同じ開発対象を理解できる状態を維持する。

## 2. 管理単位

### ユースケース

利用者が目的を達成する一連の操作を表す。

プロジェクト内でUC-001のような識別子を付ける。
一つのユースケースを複数Issueへ分割しても、対応関係を維持する。

### Issue

実装または調査・検証が可能な作業単位を表す。

### Pull Request

一つの目的を達成する変更差分を表す。
原則として一つのIssueに対応させる。

## 3. Issueの種類

### ユースケースIssue

記載する内容:

- 利用者
- 達成したい目的
- 前提条件
- 基本フロー
- 代替・異常フロー
- 受入条件
- 対象外
- 関連するユースケースID

### バグIssue

記載する内容:

- 再現環境
- 再現手順
- 期待する結果
- 実際の結果
- 影響範囲
- 修正の受入条件
- 秘密や個人情報を除いた証跡

### 技術タスクIssue

記載する内容:

- 解決する技術的な問題
- 変更の目的
- 対象範囲
- 完了時に確認できる成果
- 検証方法
- 互換性・移行・運用への影響

調査タスクでは「調査した」だけを完了条件にしない。
調査結果、選択肢、判断材料などの成果を定義する。

## 4. 状態

| 状態 | 意味 |
|---|---|
| Backlog | 候補として登録され、分析・具体化が必要 |
| Ready | 実装計画と着手に必要な条件を満たした |
| In Progress | 計画・実装・テストを進めている |
| In Review | PRのレビュー・修正を行っている |
| Done | DoDを満たし完了した |
| Blocked | 外部依存や未決判断で進められない |

Blockedには、理由、解除条件、担当者を記載する。
解除後に戻る状態も分かるようにする。

これらは運用上の状態であり、
GitHub Projectsやラベルの自動作成をこの基盤が行うわけではない。

## 5. Readyの条件

- [ ] 目的と利用者価値が説明されている
- [ ] 対象範囲と対象外が明確である
- [ ] 受入条件が検証可能である
- [ ] 実装結果を左右する仕様の不明点が解消している
- [ ] 主要な影響範囲が把握されている
- [ ] 依存Issueや制約が明示されている
- [ ] 実装・検証可能な作業量に分割されている

すべての変更ファイルや内部実装が決定済みである必要はない。
それらは実装計画で具体化する。

## 6. 受入条件の書き方

入力・操作・前提に対して、観測可能な結果を記載する。

例:

- 正しい入力で登録すると、保存した明細が一覧へ表示される
- 必須項目が空の場合、保存されず入力エラーが表示される
- 権限のない利用者は対象データを取得できない

避ける例:

- いい感じに動く
- 使いやすくする
- 問題がないこと
- テストを書く

「テストを書く」は作業内容であり、利用者視点の受入条件とは区別する。

必要に応じてAC-1、AC-2のような識別子を付け、
テストや確認結果と対応させる。

## 7. Issueの分割

次の場合は分割を検討する。

- 一つのPRで複数の独立した目的を扱う
- レビューや検証の範囲が大きすぎる
- 不確実な調査と実装を分けた方がよい
- 依存関係のため、順序を明確にする必要がある

UIだけ、APIだけという技術層の分割が常に適切とは限らない。
可能なら、小さくても利用者価値を確認できる単位を優先する。

## 8. 優先順位と担当

人間が次を考慮して決定する。

- 利用者への影響
- 緊急性
- 他の作業への依存
- リスク
- 実装・検証の見積もり

AIは判断材料を整理するが、業務上の優先順位を勝手に確定しない。

## 9. 着手後の変更

受入条件や対象範囲を変更する場合:

1. 変更理由を記録する
2. 元の条件との差を明確にする
3. 計画・テストへの影響を確認する
4. 必要な判断を人間に求める
5. Issueと関連文書を更新する

新しい要望を黙って追加しない。
現在のIssueから分離できる場合は後続Issueとする。

## 10. PRとの関連付け

- マージによってIssueを完了できる場合: Closes #番号
- 一部対応や関連付けのみの場合: Refs #番号

受入条件が残っているIssueを、PRの自動クローズだけで完了扱いしない。

## 11. 外部操作

Issue作成、コメント投稿、ラベル変更は外部への書き込みである。
ユーザーの依頼で許可された範囲で実行する。

分析や下書きの依頼だけを、投稿の許可と解釈しない。

## 12. 完了

Doneへの変更はdefinition-of-done.mdに従う。
未実装・未検証・未受入の事項を残したまま完了としない。
