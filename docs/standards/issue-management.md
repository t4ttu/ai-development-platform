# Issue管理標準

## 1. 目的

要求、対象範囲、受入条件、進捗、完了状態をIssueで管理する。
人間とAIが同じ開発対象を理解できる状態を維持する。

## 2. 管理単位

### ユースケース

利用者が目的を達成する一連の操作。

プロジェクト内でUC-001のようなIDを付ける。
複数Issueへ分割しても対応関係を維持する。

### Issue

実装、調査、検証が可能な作業単位。

### Pull Request

一つの目的を達成する変更差分。
原則として一つのIssueへ対応させる。

## 3. Issueの種類

### ユースケースIssue

- 利用者と目的
- 前提条件
- 基本フロー
- 代替・異常フロー
- 受入条件
- 対象外
- ユースケースID

### バグIssue

- 発生環境
- 再現手順
- 期待結果
- 実際の結果
- 影響範囲
- 修正の受入条件
- 秘密や個人情報を除いた証跡

### 技術タスクIssue

- 解消する問題
- 作業の目的
- 対象範囲
- 期待する成果
- 検証方法
- 互換性・移行・運用への影響

調査タスクは「調査した」だけを完了条件にしない。
調査結果、選択肢、判断材料などの成果を定義する。

## 4. 状態

| 状態 | 意味 |
|---|---|
| Backlog | 候補として登録され、分析や具体化が必要 |
| Ready | 実装計画と着手に必要な条件を満たした |
| In Progress | 計画・実装・テストを進めている |
| In Review | レビューと修正を行っている |
| Done | DoDを満たして完了した |

Blockedは、進められない理由を示す補助状態として扱う。
どの状態で止まったか、解除条件、担当者を記載する。

GitHub Projectsやラベルを使用する場合は、
この状態に対応する運用をプロジェクトで設定する。
この基盤が自動設定するものではない。

## 5. Readyの条件

- [ ] 目的と利用者価値が説明されている
- [ ] 対象範囲と対象外が明確である
- [ ] 受入条件が検証可能である
- [ ] 重要な仕様の不明点が解消している
- [ ] 主要な影響範囲を把握している
- [ ] 依存Issueと制約が明示されている
- [ ] 実装・検証可能な単位に分割されている

内部実装や全変更ファイルが決定済みである必要はない。
それらは実装計画で具体化する。

## 6. 受入条件

入力、操作、前提に対して、観測可能な結果を書く。

例:

- 正しい入力で登録すると、保存した内容が表示される
- 必須項目が空なら、保存せずエラーを表示する
- 権限のない利用者は対象データを取得できない

避ける表現:

- いい感じに動く
- 問題がない
- 使いやすくする
- テストを書く

「テストを書く」は作業内容であり、
利用者視点の受入条件とは区別する。

必要に応じてAC-1、AC-2のようなIDを付け、
実装や検証結果と対応させる。

## 7. 分割

次の場合は分割を検討する。

- 独立した目的が複数含まれる
- レビューや検証の範囲が大きすぎる
- 不確実な調査と実装を分けた方がよい
- 依存関係を明確にする必要がある

可能なら、小さくても利用者価値を確認できる単位を優先する。
技術層ごとに分けることだけを目的にしない。

## 8. 優先順位

人間が次を考慮して決定する。

- 利用者への影響
- 緊急性
- 他の作業との依存関係
- リスク
- 実装と検証の見積もり

AIは判断材料を整理する。

## 9. 着手後の変更

1. 変更理由を記録する。
2. 元の条件との差を明確にする。
3. 計画と検証への影響を確認する。
4. 必要な判断を人間へ求める。
5. Issueと関連文書を更新する。

新しい要望を黙って追加しない。
分離できる要望は後続Issueとする。

## 10. PRとの関連付け

- マージでIssueを完了できる場合: Closes #番号
- 一部対応や関連付けのみの場合: Refs #番号

受入条件が残っているIssueを、自動クローズだけで完了扱いしない。

### 作業記録との関連付け

分析、計画、検証結果はdocs/work/<Issue番号>/へ置く。

- IssueまたはPRから、該当ディレクトリへ辿れるようにする
- 作業記録の先頭に対象Issueへのリンクを書く

片方向のリンクだけにしない。
配置と運用はdocs/work/README.mdを参照する。

## 11. 外部操作

Issue作成やコメント投稿は外部への書き込みである。
依頼で許可された範囲で実行する。

分析や下書きの依頼だけを投稿の許可と解釈しない。

## 12. 完了

Doneへの変更はdefinition-of-done.mdに従う。
未実装、未検証、未受入の事項を隠して完了にしない。
