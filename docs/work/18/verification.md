### 方式A: 履歴を共有しない

```
コミット数: 1  / 派生点: 47479f3

--- 9.1 未取り込みの一覧 ---
94dc9b9 docs: README §1/§9 を履歴共有あり・なしの2方式へ対応 (#18)

--- 9.3 取り込む ---
cherry-pick exit=0

--- 9.4 PLATFORM_BASE を進める ---
--- 9.1 再実行 ---
出力: []
check.sh exit=0
```

履歴が1コミットになり、`PLATFORM_BASE` の記録を起点に
基盤の改善を検出できた。取り込んで記録を進めると一覧が空になった。

### 方式B: 履歴を共有する

```
コミット数: 12

--- 9.1 未取り込みの一覧 ---
94dc9b9 docs: README §1/§9 を履歴共有あり・なしの2方式へ対応 (#18)

--- 9.3 取り込む ---
cherry-pick exit=0

--- 9.1 再実行 ---
出力: []
check.sh exit=0
```

`--cherry-pick --right-only` により、取り込み後は一覧が空になった。

### 必須チェック

## 未実施項目と理由

- **`gh repo create --template` の実行**: 方式Aの入口のうち、GitHubのテンプレートから作る経路は新しいリポジトリを作らないと確認できない。cloneして履歴を作り直す経路で検証した。どちらも「履歴を共有しない＋PLATFORM_BASE」という同じ状態になるため、§9 の手順は共通
- **競合時の挙動**: cherry-pickが競合する場合を再現していない
- **検証手順の常設**: 両方式の派生を作る検証を自動化していない

## 残るリスク

- **`PLATFORM_BASE` の更新漏れ**: 方式Aの判定は記録の正しさに依存する。更新を忘れると取り込み済みの変更が出続ける。機械的な検査は無い。README §1.2 と §9.4 に明記した
- **手順が2系統**: README が長くなった。1.1 に判断基準を置いて迷わないようにしたが、読み飛ばすと誤った手順を実行しうる
- **方式Aで一部だけ取り込んだ場合**: `PLATFORM_BASE` に記録するSHAの選び方が運用者の判断になる。README に「取り込んだ最後のコミットのSHA」と書いたが、取り込みが連続していない場合は正確に表現できない
- **テンプレートボタンの誤用**: 方式Bを選びたい人が「Use this template」を押すと履歴が共有されない。1.1 で方式を選ばせる構成にしたが、ボタンは常に見える
