## 実行した手順とコマンド

ローカルの基盤から派生プロジェクトを作り、§1 と §9 を通して実行した。
基盤側の新しい改善の代わりに `platform/feature/9` を参照先として使った。

### §1.1 リポジトリを作る

```
$ git clone --branch main <基盤> <派生先>
$ git remote rename origin platform
リモート: platform
HEAD: 695d6e3 fix: コピー経路の不具合を修正 (#15) (#16)
```

### 派生プロジェクト側で独自の変更を加える

```
HEAD: 976124f feat: kakeibo固有の変更
```

### §9.1 未取り込みの基盤変更を一覧する

```
$ git fetch platform
$ git log --oneline HEAD..platform/feature/9
36f394e wip: README §1/§9 を書き換え (#9)
```

基盤側にだけある変更が一覧できた。

### §9.2 内容を確認する

```
$ git diff --stat HEAD...platform/feature/9 -- README.md
 README.md | 117 +++++++++++++++++++++++++---------
 1 file changed, 97 insertions(+), 20 deletions(-)
```

### §9.3 取り込む

```
$ git switch -c platform-update
$ git cherry-pick 36f394e
結果: 0327cbc wip: README §1/§9 を書き換え (#9)
```

SHAが変わっていることに注意。cherry-pickは新しいコミットを作る。

### §9.4 取り込み後の確認

```
$ ./scripts/check.sh
check.sh exit=0
```

## 検出した不具合

### 単純な2点比較では取り込み済みを判定できない（修正済み）

当初 README §9.1 には `git log --oneline HEAD..platform/main` と記載し、
「出力が空なら取り込み済み」と説明していた。

通し実行の最後で、**取り込み後も同じコミットが出続ける**ことが分かった。

```
$ git log --oneline HEAD..platform/feature/9   # cherry-pick 後
36f394e wip: README §1/§9 を書き換え (#9)
```

原因は、cherry-pickが新しいSHAのコミットを作るため、
元のコミットが祖先に入らないこと。
2点比較は祖先関係だけを見るため、取り込み済みと判定できない。

代替手段を実測で比較した。

| コマンド | 取り込み後の出力 | 判定 |
|---|---|---|
| `git log --oneline HEAD..platform/feature/9` | コミットが出続ける | 使えない |
| `git log --oneline --cherry-pick --right-only HEAD...platform/feature/9` | 空 | **正しい** |
| `git cherry HEAD platform/feature/9` | `- 36f394e...` | 正しい（`-` は取り込み済み） |

`--cherry-pick` はパッチ等価なコミットを除外する。
README §9.1 をこちらへ修正し、2点比較を使わない理由も明記した。

§9.4 へ「取り込んだ変更が一覧から消えたことを確認する」を追加した。

### この不具合の意味

手順を文書に書くだけでは、誤りに気付けなかった。
通して実行したことで、最後の1手順（取り込み後の確認）が
成立しないことが分かった。

## 未実施項目と理由

- **GitHub上での実施**: `git remote add origin <新しいリポジトリ>` と `git push -u origin main` は、新しいリポジトリを作らないと確認できない。ローカルのclone・リモート操作までを確認した
- **ラベル作成の確認**: §1.4 の `gh label create` は、基盤リポジトリで既に実施済みのため新規実行していない。#3 で動作を確認している
- **競合時の挙動**: cherry-pickが競合する場合の手順（§9.4 の4）は、競合を再現していないため未確認
- **検証手順の常設**: 派生プロジェクトを作る検証を自動化していない

## 残るリスク

- **履歴の混在**: 派生プロジェクトの履歴の根元に基盤の開発履歴が残る。`git log` が基盤のコミットを含むため、アプリの履歴として読むときに混ざる
- **platform リモートの削除**: 削除すると差分計算ができなくなる。README に明記したが、機械的な防止策は無い
- **判定コマンドの複雑さ**: `--cherry-pick --right-only` と3点比較は直感的でない。誤って2点比較を使うと取り込み済みの変更が出続ける。README に理由を明記したが、間違える余地は残る
- **基盤側の破壊的変更**: 基盤が構成を大きく変えた場合、cherry-pickが競合する。競合時の判断手順は記載したが未検証
