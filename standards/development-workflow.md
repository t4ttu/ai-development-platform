# AI駆動開発 標準ワークフロー

## 1. 目的

本ドキュメントは、AI Coding Agentを活用した
ソフトウェア開発の標準プロセスを定義する。

以下を実現することを目的とする。

- 開発工程の標準化
- AIと人間の責任分担の明確化
- 開発品質の維持
- 手戻りの削減
- 複数プロジェクトでの再利用

## 2. 基本方針

- アジャイル開発を基本とする
- ユースケース駆動開発を採用する
- GitHub Issuesを開発管理の中心とする
- Issue単位で設計・実装・テストを行う
- AIは開発作業を支援し、重要な意思決定は人間が行う
- 必要最小限のドキュメントを維持する
- すべての変更は受入条件に基づいて検証する

## 3. 開発工程

開発は以下の工程で実施する。

1. 要求整理
2. Issue作成
3. Issue分析
4. 実装計画
5. 実装
6. テスト
7. コードレビュー
8. 受入確認
9. 完了・振り返り

## 4. 工程定義

### 4.1 要求整理

#### 目的
ユーザーの課題と実現したい価値を明確にする。

#### インプット
- ユーザーの要望
- プロダクト方針
- 既存機能

#### 実施内容
- ユーザーストーリーの整理
- ユースケースの洗い出し
- 優先順位の検討

#### アウトプット
- ユーザーストーリー
- ユースケース一覧

#### 責任分担
- 人間：要求・優先順位の決定
- AI：要求整理・ユースケースの提案

### 4.2 Issue作成

#### 目的
開発対象を実装・検証可能な単位にする。

#### インプット
- ユースケース
- プロダクト方針

#### 実施内容
- Issueの作成
- 受入条件の定義
- 対象範囲・対象外の明確化

#### アウトプット
- GitHub Issue

#### 責任分担
- 人間：Issueの承認
- AI：Issue内容の具体化

### 4.3 Issue分析

#### 目的
実装前に要求と既存システムへの影響を把握する。

#### インプット
- GitHub Issue
- 関連ドキュメント
- 既存ソースコード

#### 実施内容
- 受入条件の確認
- 関連機能の調査
- 不明点・矛盾の抽出
- 影響範囲の特定

#### アウトプット
- Issue分析結果
- 不明点一覧
- 影響範囲

#### 責任分担
- 人間：重要な不明点の判断
- AI：調査・分析

### 4.4 実装計画

#### 目的
実装方針と変更範囲を明確にする。

#### インプット
- 分析済みIssue
- アーキテクチャ
- 既存コード

#### 実施内容
- 実装方式の検討
- 変更ファイルの特定
- DB/API変更の検討
- テスト方針の作成

#### アウトプット
- 実装計画
- テスト計画

#### 責任分担
- 人間：重要な設計変更の承認
- AI：実装計画の作成

### 4.5 実装

#### 目的
受入条件に基づいて機能を実装する。

#### インプット
- GitHub Issue
- 実装計画
- 開発ルール

#### 実施内容
- ソースコードの実装
- 必要なDB変更
- テストコードの追加

#### アウトプット
- ソースコード
- テストコード
- 変更概要

#### 責任分担
- 人間：必要に応じた判断
- AI：実装

### 4.6 テスト

#### 目的
実装が受入条件を満たしていることを確認する。

#### インプット
- 受入条件
- 実装コード
- テストコード

#### 実施内容
- 静的解析
- 単体テスト
- 結合テスト
- 必要に応じたE2Eテスト

#### アウトプット
- テスト結果
- 不具合一覧

#### 責任分担
- 人間：重要な検証結果の確認
- AI：テスト作成・実行・修正

### 4.7 コードレビュー

#### 目的
実装の品質と設計上の妥当性を確認する。

#### インプット
- Pull Request
- GitHub Issue
- テスト結果

#### 実施内容
- 仕様との整合性確認
- コード品質の確認
- セキュリティ確認
- 変更範囲の確認

#### アウトプット
- レビュー結果
- 修正指摘

#### 責任分担
- 人間：最終承認
- AI：レビュー支援

### 4.8 受入確認

#### 目的
ユーザー視点で要求が実現されていることを確認する。

#### インプット
- GitHub Issue
- 受入条件
- 動作するアプリケーション

#### 実施内容
- ユースケースに沿った動作確認
- 受入条件の確認
- 不足機能の確認

#### アウトプット
- 受入結果
- 修正事項

#### 責任分担
- 人間：受入判断
- AI：確認支援

### 4.9 完了・振り返り

#### 目的
開発結果を確定し、次の開発へ改善を反映する。

#### インプット
- 承認済みPull Request
- テスト結果
- 受入結果

#### 実施内容
- Pull Requestのマージ
- Issueの完了
- 課題・改善点の整理

#### アウトプット
- 完了Issue
- マージ済みコード
- 改善事項

#### 責任分担
- 人間：マージ・完了判断
- AI：結果整理・改善提案

## 5. 工程の基本ルール

- IssueがReadyになる前に実装を開始しない
- 重要な仕様の不明点がある場合は実装を停止する
- 原則として1つのIssueに対して1つのPull Requestを作成する
- Issueの対象外となる変更は原則行わない
- テスト未実行の状態を成功として報告しない
- 受入条件を満たさないIssueは完了としない
- 不具合修正や仕様変更もIssueで管理する

## 6. Definition of Done

Issueを完了するには、少なくとも以下を満たす。

- [ ] 受入条件を満たしている
- [ ] 必要なテストが成功している
- [ ] 既存機能への影響を確認している
- [ ] コードレビューが完了している
- [ ] 必要なドキュメントが更新されている
- [ ] 人間による受入が完了している
- [ ] Pull Requestがマージされている

詳細は `definition-of-done.md` を参照する。

## 7. 継続的改善

開発中に確認された問題は、次の観点で分類する。

- 要求・Issueの情報不足
- AIによる仕様の誤解
- アーキテクチャ・設計の問題
- Rulesの不足
- Skillsの不足
- テストの不足

複数プロジェクトで共通する問題は、
AI駆動開発基盤側の改善対象とする。

プロジェクト固有の問題は、
各プロジェクト内で解決する。
